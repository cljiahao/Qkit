# dashboard

## Purpose

The authenticated vendor area — a shared header/nav shell wrapping the live order board plus sub-routes for booth management, order history, billing, account, board preferences, analytics, and support.

A second test asserts the structural precondition for sticky positioning: the header's immediate parent carries both `contents` and `print:hidden` classes (jsdom doesn't compute layout, so it can't prove the header actually sticks on scroll, but it can prove the wrapper isn't a plain box that would break the containing block).
- `layout.tsx` — `DashboardLayout({ children })` server component: resolves `user`/`vendor`/`entitlement` via `loadEntitlement()`, redirects to `/login` if signed out, `/admin` if the user `isAdmin()`, `/onboarding` if there's no vendor row yet (before the header shell paints, avoiding a blank-flash). Renders `DashboardNav` inside a `contents print:hidden` `<div>` — not a `<header>` wrapper, since `@merqo/ui`'s `DashboardNav` already renders its own sticky/bordered `<header>` internally. `contents` is load-bearing, not decorative: `@merqo/ui`'s inner `<header>` is `position: sticky`, so a plain wrapper `<div>` (no `contents`) would itself become the header's containing block at exactly the header's own height, leaving it no room to stick; `display: contents` removes the wrapper's own box so `<header>` becomes a direct flex item of this component's `min-h-screen flex flex-col` container instead, restoring the pre-migration containing-block structure. `print:hidden` still applies under `@media print` regardless of the wrapper's own `display` value. Plus a `signOut` server action, and `DashboardTour` (onboarding tour, gated on `vendor.tour_seen_at`).
- `loading.tsx` — `Loading()`: the segment's Suspense fallback, a centered spinning `Loader2`, shown while a nested page is slow to resolve.
- `order-actions.test.ts` — vitest suite mocking the Supabase server client's fluent chain to unit-test `advanceOrder`/`confirmOrderPayment`/`cancelOrder`/`restoreAutoCompleted`/`sweepReadyOrders`, including the optimistic-concurrency "0 rows updated → refresh" path, the no-refund-rail rejection, and (mocking `notifyCustomer`) that `advanceOrder` calls it with the right `vendor_id`/`notify_ref`/message only on a `'ready'` transition, and that a `notifyCustomer` rejection never changes `advanceOrder`'s own success result.
- `order-actions.ts` — server actions for the order board, gated by `getUser()` and RLS (never service-role): `advanceOrder(orderId)` moves an order to its `ADVANCE`-derived next status guarded by a conditional `UPDATE ... WHERE status = <read status>` (so a concurrent change yields "Order changed — please refresh" instead of clobbering it) — fires instantly, no confirmation gate, since `OrderCard` backs it with a short undo window instead (see `revertOrderAdvance`); on a successful transition to `'ready'`, also fires `notifyCustomer` (`@/lib/merqo-customer-notify`, `notify_ref` `` `qkit:${orderId}` `` — the customer's Telegram-connect flow, order/[boothId]/[orderNumber]'s `TelegramConnect`) wrapped in try/catch so a merqo-side failure never changes this action's own returned result; `revertOrderAdvance(orderId, revertTo, revertFrom, prevPaymentStatus)` undoes a just-made `advanceOrder` within that window — rejects any `(revertTo, revertFrom)` pair that isn't `ADVANCE`'s own next-status mapping (can't be used to jump an order to an arbitrary status), and undoes the payment auto-confirm `buildAdvancePatch` applied if `prevPaymentStatus` shows it actually happened; `confirmOrderPayment(orderId)` (the vendor's "Confirm payment" tap — cut over to paykit) calls paykit's `createCheckout`/`confirmCheckout` (`@/lib/paykit/client`, the authenticated vendor's own id doubles as paykit's `vendor_id` since RLS already scopes `loadOwnOrder` to the caller's own booths) and then mirrors the confirm into the local `payment_status` (idempotent, rejects `not_required`/cancelled; a failed local mirror write still reports success since paykit already recorded the confirm); `cancelOrder(orderId)` cancels a non-terminal order but refuses one with `payment_status: "confirmed"` (no refund rail — money already "real" can't be cancelled away) — one exception to "non-terminal": an order the auto-clear sweep completed (`auto_completed: true`) is still cancellable, since that completion wasn't a deliberate vendor decision the way a manual "Mark Picked Up" is; cancelling one also clears `auto_completed`/`completed_at` so the now-cancelled order doesn't carry stale "this was completed" bookkeeping; `bumpOrder(orderId)` stamps `priority_bumped_at` to move a live order to the front of its status lane, an explicit one-time vendor override with no cap on how often a live order can be re-bumped; `sweepReadyOrders()` is the ready-order auto-clear sweep — no id param, bulk-flips every `'ready'` order across the caller's own booths whose `ready_at` is older than the vendor's `board_settings.ready_auto_clear_min` (minutes; `null` disables the sweep) to `'completed'`, stamping `auto_completed: true` so it's distinguishable from a vendor's own "Mark Picked Up" tap; called on a 30s client poll from `realtime-order-board.tsx` (only while `ready_auto_clear_min` is set) rather than a DB cron job, returns `void` and only logs on failure since it's a background sweep with no toast, and the next poll simply retries — `OrderCard`'s "Mark Picked Up" shows a matching drain-bar countdown (`readyAutoClearMs` prop, `.autoclear-bar`) so this isn't invisible until the order just vanishes; `restoreAutoCompleted(orderId)` is the undo for a sweep that fired before the vendor actually collected the order — flips a `'completed'`+`auto_completed: true` order back to `'ready'` (clearing `completed_at`/`auto_completed`), rejecting any order that isn't in exactly that state (in particular, a vendor's own manual completion is never restorable through this path) — deliberately narrower than `revertOrderAdvance`'s short undo window since this is reached from a fresh page load (the completed-orders history list) with no client-held prior state.
- `page.tsx` — `DashboardPage()` (server, `revalidate = 0`): reuses the layout's primed `requireEntitledVendor()` cache, reads the vendor's `booths` (id/name/is_active/hours) and computes `open`/closed per booth via `isBoothOpen`, reads non-terminal `orders` (`BOARD_ORDER_COLUMNS`) across those booths, and renders `RealtimeOrderBoard` with a `loadError` flag (a DB read error surfaces a retry banner instead of masquerading as an empty board). When `board_settings.daily_order_number_reset` is on, also reads each booth's first `order_number` of the SGT day (`sgtStartOfDayIso`, one combined query across all booths, skipped entirely otherwise) and passes it down as `dailyOrderNumberBaselines`.
- `plan/` — billing/plan page (current tier, pass countdown, upgrade CTAs).
- `profile/` — vendor account profile page (stall name, avatar, display name, password).
- `realtime-order-board.tsx` — `RealtimeOrderBoard({ booths, initialOrders, boardSettings, loadError, dailyOrderNumberBaselines })` client component: the live order board itself. A **Select** button (shown only while at least one visible order is `preparing`) enters batch mark-ready mode: each `preparing` `OrderCard` grows a checkbox, and a **Mark N Ready** button calls the existing `advanceOrder` action once per selected id (`Promise.all`, no new bulk RPC — each id still goes through its own optimistic-concurrency guard) and toasts a success/failure count. The header stacks (title above the button row) below `sm` and lets the button row wrap, rather than the fixed side-by-side row that used to run buttons off the edge of a phone screen; the "Booths · N/M open" button drops "Booths"/"open" below `sm` (icon + count only, `aria-label` carries the full name regardless of breakpoint), and "+ New order" keeps "New" at every width, dropping only "order" below `sm` — so four header controls fit a phone width without wrapping into a wall of pills, without a bare icon-only button a vendor has to guess at. Subscribes via `useRealtimeOrders(boothIds, initialOrders, handleNewOrder)`, plays a sound and fires a toast/desktop notification (`fireNewOrderNotification`) on a new order while the tab is hidden, tracks an "away" badge reflected into `document.title`, filters/sorts active orders (`sortActiveOrders`, `isTerminal`) with an earliest/latest sort-order toggle, renders a booth-filter `Select` dropdown when multi-booth (scales to any booth count without a wall of tabs — each option keeps the live count, open/closed state, and `boothColor()` dot), an empty/"No booths yet" state linking to `/dashboard/booths/new`, an idle "All caught up" state, and a grid of `OrderCard`s otherwise, each given a `displayOrderNumber(order.order_number, dailyOrderNumberBaselines[order.booth_id] ?? null)` (see `@/lib/orders`) so the daily-reset display number (when on) is computed once here rather than in every card. Tracks `undoWindowIds` (via each card's `onUndoWindowChange`) and keeps those order ids in the active filter even once terminal, so a card mid-undo-window doesn't get pulled out from under the vendor by its own advance's realtime echo. Per-booth open/paused control via the shared `BoothRow` + `BoothToggle` (name, `(outside hours)` note, and a single `Button` calling `toggleBoothActive` from `./booths/actions` instantly with an undo toast — `Pause` icon + "Open" + emerald when open, `Play` icon + "Paused" + muted when paused, same play/pause convention as a media player, wrapped in a `Tooltip` naming the action a hover reveals; icon-only was tried first and dropped — without hover on a phone it read as ambiguous — and before that a two-segment `Open`/`Paused` `ToggleGroup`, which read clearly but cost 2-3x the width for what's one binary action): a single booth gets `BoothRow` inline under the header; a vendor with several booths gets a "Booths · N/M open" header button that opens a `Dialog` listing every `BoothRow` (keyed on the full `booths` list, not the count/schedule-filtered `visibleBooths`, so a paused booth with nothing in flight stays reachable), keeping the board itself free of a pause-toggle row that would otherwise wrap and grow with every extra booth — but once that vendor has filtered the board down to one booth via the `Select` below, the header renders `BoothToggle` directly for that exact booth instead of going through `BoothRow` at all (the `Select` right below already says which booth this is, so a bordered row around just the toggle button would be a border around a border), so pausing the booth you're already looking at doesn't mean re-finding it in a dialog. `visibleBooths` (the `Select`'s source, and what collapses `multiBooth`) keeps a booth visible if it's active, has an order in flight, _or_ is the one `filter` currently points at — without that last clause, pausing the filtered booth with nothing in flight dropped it from the list on the very same render, collapsing `multiBooth` to `false` and yanking both the `Select` and the header's own `BoothToggle` out from under the tap that had just paused it. A header "+ New order" button opens `WalkupOrderDialog` (`./walkup-order-dialog`), preselecting the currently-filtered booth if one's chosen. This is the quick, instant pause; `./booths/close-booth-control.tsx` (in the booth-edit form) is the deliberately more guarded close path.

- `walkup-actions.test.ts` — vitest suite (mocked `createServerClient().rpc`) covering `placeWalkupOrder`'s invalid-booth/invalid-input rejection (no RPC call), the happy path's exact `place_walkup_order` args including `p_paid`, the `paid=true` passthrough, its RAISE-prefix-to-message mapping (`ORDER_UNAUTHORIZED`/`ORDER_SOLD_OUT`/`ORDER_RATE_LIMITED`), the generic-message+log fallback for an unrecognized error, and a malformed-success-payload guard.
- `walkup-actions.ts` — `placeWalkupOrder(boothId, input: PlaceOrderInput, paid: boolean)` server action: validates `input` with the same `placeOrderSchema` the customer cart uses, then calls the `place_walkup_order` RPC (migration 0061, originally 0060) with `p_booth_id`/`p_customer_name`/`p_items`/`p_paid`. `paid` lets staff mark payment as already collected at the counter in the same step as placing the order; the RPC ignores it for a booth that doesn't take payment. Maps its RAISE-prefixed errors to vendor-facing messages (mirrors `o/[code]/actions.ts#messageFor`, minus the customer-only `ORDER_EXPIRED`/`ORDER_UNSERVABLE` cases, since a walk-up order isn't gated by the booth's schedule).
- `walkup-menu-actions.test.ts` — vitest suite (mocked Supabase chain + `rpc`) covering `getWalkupMenu`'s invalid-id short-circuit, the RLS-scoped not-found → null, the happy path (parsed menu items + `booth_remaining_stock` result + `expectsPayment`/`paymentKind`), a configured-payment-kind case, the stripe-is-dark case, and dropping a malformed menu item entry.
- `walkup-menu-actions.ts` — `getWalkupMenu(boothId)` server action: reads a booth's `menu_items` and `payment` config (RLS-scoped to the caller's own booths, same as the booth-edit page) plus its live `booth_remaining_stock` RPC result, for `WalkupOrderDialog` to render. Also derives `expectsPayment`/`paymentKind` from the booth's payment config via the local `markerKind` (a live, non-stripe kind counts; stripe is reserved but dark, same rule `place_walkup_order` applies) — reads just the `kind` discriminant rather than `parsePaymentConfig`'s full-shape parse, since `booths.payment` now stores only the minimal `{kind}` marker the paykit cutover writes (see `booths/actions.ts`), which the strict parse would reject outright. Unfiltered by `available`: same as the customer flow, an unavailable item is rejected server-side rather than hidden client-side.
- `walkup-order-dialog.dom.test.tsx` — RTL tests for `WalkupOrderDialog`: fetches the selected booth's menu once opened, adds a plain item and submits (asserts the exact `placeWalkupOrder` call including `paid=false` + dialog close), the payment-collected switch appearing only when the booth expects payment and its state reaching `placeWalkupOrder`'s third argument, a no-booths empty state that skips the fetch entirely, and the disabled-submit-with-empty-cart state.
- `walkup-order-dialog.tsx` — `WalkupOrderDialog({ open, onOpenChange, booths, initialBoothId? })` client component: a leaner, dashboard-scoped rebuild of `OrderForm`'s menu/cart UX (same `ItemCustomizer`, `cartKey`/`cartTotal`/`sumOptionDeltas`, stock-capping) for staff keying in a walk-up order. Deliberately drops `OrderForm`'s customer-only machinery (session/localStorage cart persistence, recent-orders, funnel events, redirect-on-success) and `PayPanel`'s customer-voiced polling UI; the one payment control it does offer is a plain "Payment collected" `Switch`, shown only when `getWalkupMenu` reports `expectsPayment`, for the common counter case of staff already knowing the outcome (cash, tap-to-pay) before the ticket is placed. Split-pane `Dialog` (menu grid left, an order-summary column right holding the cart, payment switch, customer-name field, and submit button) rather than a single scrolling sheet: a staff member building a multi-item order can see what's in the cart and hit submit without scrolling past the whole menu; panes stack on narrow screens. A booth `Select` appears only when more than one active booth is offered; the menu (re)fetches via `getWalkupMenu` whenever the open booth changes, resetting the payment switch. Submits through `placeWalkupOrder`, toasts, and closes on success — the board itself updates via its existing realtime subscription, no manual state injection needed.

## Connectivity

`layout.tsx` gates every route under `/dashboard` (auth/vendor/admin redirects) and renders `dashboard-nav.tsx` around `{children}`; `page.tsx` is the `/dashboard` index route and renders `realtime-order-board.tsx`, which calls the order-mutation actions in `order-actions.ts` indirectly via `OrderCard` and subscribes through `@/hooks/use-realtime-orders`. `dashboard-nav.tsx` links out to `completed/`, `booths/`, `plan/`, `profile/`, `settings/`, `stats/`, `feedback/` — the dashboard's sub-routes for order history, booth management, billing, account, board preferences, analytics, and support respectively. `tour-actions.ts` is called by `DashboardTour` (in `@/components`) once the tour completes.
