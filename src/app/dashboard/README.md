# dashboard

## Purpose

The authenticated vendor area — a shared header/nav shell wrapping the live order board plus sub-routes for booth management, order history, billing, account, board preferences, analytics, and support.

## Contents

- `booths/` — booth list, create/edit form, and printable QR-code sub-routes.
- `completed/` — paginated history of the vendor's completed orders (own README).
- `dashboard-nav.dom.test.tsx` — RTL/jsdom tests for `DashboardNav`: asserts the inline nav links (Orders/Completed/Booths/Stats, no Plan link) and the account-menu item order (Profile, Board settings, Plan, Get help, Feedback, then Sign out).
- `dashboard-nav.tsx` — `DashboardNav({ signOut, vendorName, avatarUrl, tier })` client component: the sticky header row. Left side is a mobile burger (`Menu`/`X`) plus inline `Orders`/`Completed`/`Booths`/`Stats` links (`LINKS` array) from `sm` up, with active-route highlighting via `isActive`/`usePathname`; right side is an account dropdown (avatar with `initials()` fallback, a `TierBadge` reflecting the vendor's plan tier) linking to Profile, Board settings, Plan, and opening `Get help`/`Feedback` `Sheet` drawers (rendering `SupportForm`/`FeedbackForm`) before a `signOut` form submit.
- `feedback/` — vendor-facing "share feedback about qkit" page.
- `layout.tsx` — `DashboardLayout({ children })` server component: resolves `user`/`vendor`/`entitlement` via `loadEntitlement()`, redirects to `/login` if signed out, `/admin` if the user `isAdmin()`, `/onboarding` if there's no vendor row yet (before the header shell paints, avoiding a blank-flash). Renders the sticky header with `DashboardNav`, a `signOut` server action, and `DashboardTour` (onboarding tour, gated on `vendor.tour_seen_at`).
- `loading.tsx` — `Loading()`: the segment's Suspense fallback, a centered spinning `Loader2`, shown while a nested page is slow to resolve.
- `order-actions.test.ts` — vitest suite mocking the Supabase server client's fluent chain to unit-test `advanceOrder`/`confirmOrderPayment`/`cancelOrder`, including the optimistic-concurrency "0 rows updated → refresh" path and the no-refund-rail rejection.
- `order-actions.ts` — server actions for the order board, gated by `getUser()` and RLS (never service-role): `advanceOrder(orderId)` moves an order to its `ADVANCE`-derived next status guarded by a conditional `UPDATE ... WHERE status = <read status>` (so a concurrent change yields "Order changed — please refresh" instead of clobbering it) — fires instantly, no confirmation gate, since `OrderCard` backs it with a short undo window instead (see `revertOrderAdvance`); `revertOrderAdvance(orderId, revertTo, revertFrom, prevPaymentStatus)` undoes a just-made `advanceOrder` within that window — rejects any `(revertTo, revertFrom)` pair that isn't `ADVANCE`'s own next-status mapping (can't be used to jump an order to an arbitrary status), and undoes the payment auto-confirm `buildAdvancePatch` applied if `prevPaymentStatus` shows it actually happened; `confirmOrderPayment(orderId)` marks a claimed order's `payment_status` as `confirmed` (idempotent, rejects `not_required`/cancelled); `cancelOrder(orderId)` cancels a non-terminal order but refuses one with `payment_status: "confirmed"` (no refund rail — money already "real" can't be cancelled away).
- `page.tsx` — `DashboardPage()` (server, `revalidate = 0`): reuses the layout's primed `requireEntitledVendor()` cache, reads the vendor's `booths` (id/name/is_active/hours) and computes `open`/closed per booth via `isBoothOpen`, reads non-terminal `orders` (`BOARD_ORDER_COLUMNS`) across those booths, and renders `RealtimeOrderBoard` with a `loadError` flag (a DB read error surfaces a retry banner instead of masquerading as an empty board). When `board_settings.daily_order_number_reset` is on, also reads each booth's first `order_number` of the SGT day (`sgtStartOfDayIso`, one combined query across all booths, skipped entirely otherwise) and passes it down as `dailyOrderNumberBaselines`.
- `plan/` — billing/plan page (current tier, pass countdown, upgrade CTAs).
- `profile/` — vendor account profile page (stall name, avatar, display name, password).
- `realtime-order-board.tsx` — `RealtimeOrderBoard({ booths, initialOrders, boardSettings, loadError, dailyOrderNumberBaselines })` client component: the live order board itself. The header stacks (title above the button row) below `sm` and lets the button row wrap, rather than the fixed side-by-side row that used to run buttons off the edge of a phone screen; the "Booths · N/M open" and "+ New order" buttons drop their text label below `sm` (icon + count only, `aria-label` carries the full name regardless of breakpoint) so four header controls fit a phone width without wrapping into a wall of pills. Subscribes via `useRealtimeOrders(boothIds, initialOrders, handleNewOrder)`, plays a sound and fires a toast/desktop notification (`fireNewOrderNotification`) on a new order while the tab is hidden, tracks an "away" badge reflected into `document.title`, filters/sorts active orders (`sortActiveOrders`, `isTerminal`) with an earliest/latest sort-order toggle, renders a booth-filter `Select` dropdown when multi-booth (scales to any booth count without a wall of tabs — each option keeps the live count, open/closed state, and `boothColor()` dot), an empty/"No booths yet" state linking to `/dashboard/booths/new`, an idle "All caught up" state, and a grid of `OrderCard`s otherwise, each given a `displayOrderNumber(order.order_number, dailyOrderNumberBaselines[order.booth_id] ?? null)` (see `@/lib/orders`) so the daily-reset display number (when on) is computed once here rather than in every card. Tracks `undoWindowIds` (via each card's `onUndoWindowChange`) and keeps those order ids in the active filter even once terminal, so a card mid-undo-window doesn't get pulled out from under the vendor by its own advance's realtime echo. Per-booth open/paused control via the shared `BoothRow` + `BoothToggle` (name, `(outside hours)` note, and a two-segment `Open`/`Paused` `ToggleGroup` calling `toggleBoothActive` from `./booths/actions` instantly with an undo toast — replaces a separate status word plus a `Switch`, which said the same thing twice and cost twice the width): a single booth gets `BoothRow` inline under the header; a vendor with several booths gets a "Booths · N/M open" header button that opens a `Dialog` listing every `BoothRow` (keyed on the full `booths` list, not the count/schedule-filtered `visibleBooths`, so a paused booth with nothing in flight stays reachable), keeping the board itself free of a pause-toggle row that would otherwise wrap and grow with every extra booth — but once that vendor has filtered the board down to one booth via the `Select` below, the header swaps to a compact `BoothRow` (`compact` prop) for that exact booth instead, so pausing the booth you're already looking at doesn't mean re-finding it in a dialog — `compact` drops the booth's name too (the `Select` right below already says which booth this is), leaving just the `Open`/`Paused` toggle in the header. A header "+ New order" button opens `WalkupOrderDialog` (`./walkup-order-dialog`), preselecting the currently-filtered booth if one's chosen. This is the quick, instant pause; `./booths/close-booth-control.tsx` (in the booth-edit form) is the deliberately more guarded close path.
- `realtime-order-board.dom.test.tsx` — RTL tests: the earliest/latest sort toggle, the daily order-number reset (real number when no baseline supplied, the display-rank number when one is), the per-booth `BoothToggle` (a `role="group"` of two `role="radio"` segments, inline for a single booth, gated behind the "Booths" dialog for 2+, stays reachable for a paused/empty booth, toggles + reverts on failure), and the walk-up button (opens the dialog for the sole active booth and fetches its menu; shows a no-booths state instead when nothing's active).
- `settings/` — board-preferences page: aging/overdue thresholds, the tap-undo
  window, new-order sound, desktop notifications, daily order-number reset,
  and a backup prep-time estimate, all persisted to `vendors.board_settings`.
- `stats/` — sales analytics: revenue/orders/AOV, trends, margin, busy-hours,
  top items, service speed, and reviews, gated free/pass vs. Pro, plus a
  permanent ungated snapshot for a paid event window.
- `tour-actions.ts` — `markTourSeen()` server action: best-effort stamps `vendors.tour_seen_at` for the signed-in user so the onboarding tour stops auto-running; failures are logged but never surfaced (worst case the tour just shows once more).
- `walkup-actions.test.ts` — vitest suite (mocked `createServerClient().rpc`) covering `placeWalkupOrder`'s invalid-booth/invalid-input rejection (no RPC call), the happy path's exact `place_walkup_order` args including `p_paid`, the `paid=true` passthrough, its RAISE-prefix-to-message mapping (`ORDER_UNAUTHORIZED`/`ORDER_SOLD_OUT`/`ORDER_RATE_LIMITED`), the generic-message+log fallback for an unrecognized error, and a malformed-success-payload guard.
- `walkup-actions.ts` — `placeWalkupOrder(boothId, input: PlaceOrderInput, paid: boolean)` server action: validates `input` with the same `placeOrderSchema` the customer cart uses, then calls the `place_walkup_order` RPC (migration 0061, originally 0060) with `p_booth_id`/`p_customer_name`/`p_items`/`p_paid`. `paid` lets staff mark payment as already collected at the counter in the same step as placing the order; the RPC ignores it for a booth that doesn't take payment. Maps its RAISE-prefixed errors to vendor-facing messages (mirrors `o/[code]/actions.ts#messageFor`, minus the customer-only `ORDER_EXPIRED`/`ORDER_UNSERVABLE` cases, since a walk-up order isn't gated by the booth's schedule).
- `walkup-menu-actions.test.ts` — vitest suite (mocked Supabase chain + `rpc`) covering `getWalkupMenu`'s invalid-id short-circuit, the RLS-scoped not-found → null, the happy path (parsed menu items + `booth_remaining_stock` result + `expectsPayment`/`paymentKind`), a configured-payment-kind case, the stripe-is-dark case, and dropping a malformed menu item entry.
- `walkup-menu-actions.ts` — `getWalkupMenu(boothId)` server action: reads a booth's `menu_items` and `payment` config (RLS-scoped to the caller's own booths, same as the booth-edit page) plus its live `booth_remaining_stock` RPC result, for `WalkupOrderDialog` to render. Also derives `expectsPayment`/`paymentKind` from the booth's payment config via `parsePaymentConfig` (a live, non-stripe kind counts; stripe is reserved but dark, same rule `place_walkup_order` applies) so the dialog knows whether to offer a "payment collected" toggle. Unfiltered by `available`: same as the customer flow, an unavailable item is rejected server-side rather than hidden client-side.
- `walkup-order-dialog.dom.test.tsx` — RTL tests for `WalkupOrderDialog`: fetches the selected booth's menu once opened, adds a plain item and submits (asserts the exact `placeWalkupOrder` call including `paid=false` + dialog close), the payment-collected switch appearing only when the booth expects payment and its state reaching `placeWalkupOrder`'s third argument, a no-booths empty state that skips the fetch entirely, and the disabled-submit-with-empty-cart state.
- `walkup-order-dialog.tsx` — `WalkupOrderDialog({ open, onOpenChange, booths, initialBoothId? })` client component: a leaner, dashboard-scoped rebuild of `OrderForm`'s menu/cart UX (same `ItemCustomizer`, `cartKey`/`cartTotal`/`sumOptionDeltas`, stock-capping) for staff keying in a walk-up order. Deliberately drops `OrderForm`'s customer-only machinery (session/localStorage cart persistence, recent-orders, funnel events, redirect-on-success) and `PayPanel`'s customer-voiced polling UI; the one payment control it does offer is a plain "Payment collected" `Switch`, shown only when `getWalkupMenu` reports `expectsPayment`, for the common counter case of staff already knowing the outcome (cash, tap-to-pay) before the ticket is placed. Split-pane `Dialog` (menu grid left, an order-summary column right holding the cart, payment switch, customer-name field, and submit button) rather than a single scrolling sheet: a staff member building a multi-item order can see what's in the cart and hit submit without scrolling past the whole menu; panes stack on narrow screens. A booth `Select` appears only when more than one active booth is offered; the menu (re)fetches via `getWalkupMenu` whenever the open booth changes, resetting the payment switch. Submits through `placeWalkupOrder`, toasts, and closes on success — the board itself updates via its existing realtime subscription, no manual state injection needed.

## Connectivity

`layout.tsx` gates every route under `/dashboard` (auth/vendor/admin redirects) and renders `dashboard-nav.tsx` around `{children}`; `page.tsx` is the `/dashboard` index route and renders `realtime-order-board.tsx`, which calls the order-mutation actions in `order-actions.ts` indirectly via `OrderCard` and subscribes through `@/hooks/use-realtime-orders`. `dashboard-nav.tsx` links out to `completed/`, `booths/`, `plan/`, `profile/`, `settings/`, `stats/`, `feedback/` — the dashboard's sub-routes for order history, booth management, billing, account, board preferences, analytics, and support respectively. `tour-actions.ts` is called by `DashboardTour` (in `@/components`) once the tour completes.
