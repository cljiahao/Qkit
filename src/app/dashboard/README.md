# dashboard

## Purpose

The authenticated vendor area — a shared header/nav shell wrapping the live order board plus sub-routes for booth management, order history, billing, account, board preferences, analytics, and support.

## Contents

- `booths/` — booth list, create/edit form, and printable QR-code sub-routes.
- `completed/` — paginated history of the vendor's completed orders (own README).
- `customer-screen-dialog.tsx` — `CustomerScreenButton({ booths, defaultBoothId })`, the board header's way to the public queue display (`/order/{boothId}/display`, built by `customerScreenUrl`). Its dialog offers two routes that between them cover every setup: "Open the screen" opens the display in a separate popup window (not a tab, so it can be dragged straight onto a TV, a monitor or an iPad used as an extended display, in any browser; a blocked popup is reported with a toast), and a QR code plus "Copy the link" for a device that is not attached to the computer. With more than one booth a radio group picks which, starting on the booth the board is filtered to.

- `order-actions.ts` — server actions for the order board, gated by `getUser()` and RLS (never service-role): `advanceOrder(orderId)` moves an order to its `ADVANCE`-derived next status guarded by a conditional `UPDATE ... WHERE status = <read status>` (so a concurrent change yields "Order changed — please refresh" instead of clobbering it) — fires instantly, no confirmation gate, since `OrderCard` backs it with a short undo window instead (see `revertOrderAdvance`); on a successful transition to `'ready'`, also fires `notifyCustomer` (`@/lib/merqo-customer-notify`, `notify_ref` `` `qkit:${orderId}` `` — the customer's Telegram-connect flow, order/[boothId]/[orderNumber]'s `TelegramConnect`) wrapped in try/catch so a merqo-side failure never changes this action's own returned result — gated first by `customerNotifyEnabled(supabase, userId)` (2026-08-16), a vendor-side brand-preference opt-out (`board_settings.customer_telegram_notify_enabled`, distinct from the customer's own merqo-side consent) that reads the vendor's `board_settings` and skips the call only on an explicit `false`; an unparseable/missing row (every vendor whose row predates this key) fails open, same default-true rationale as `boardSettingsSchema`'s own `.default(true)`; `revertOrderAdvance(orderId, revertTo, revertFrom, prevPaymentStatus)` undoes a just-made `advanceOrder` within that window — rejects any `(revertTo, revertFrom)` pair that isn't `ADVANCE`'s own next-status mapping (can't be used to jump an order to an arbitrary status), and undoes the payment auto-confirm `buildAdvancePatch` applied if `prevPaymentStatus` shows it actually happened; `confirmOrderPayment(orderId)` (the vendor's "Confirm payment" tap — cut over to paykit) calls paykit's `createCheckout`/`confirmCheckout` (`@/lib/paykit/client`, the authenticated vendor's own id doubles as paykit's `vendor_id` since RLS already scopes `loadOwnOrder` to the caller's own booths) and then mirrors the confirm into the local `payment_status` (idempotent, rejects `not_required`/cancelled; a failed local mirror write still reports success since paykit already recorded the confirm); `cancelOrder(orderId)` cancels a non-terminal order but refuses one with `payment_status: "confirmed"` (no refund rail — money already "real" can't be cancelled away) — one exception to "non-terminal": an order the auto-clear sweep completed (`auto_completed: true`) is still cancellable, since that completion wasn't a deliberate vendor decision the way a manual "Mark Picked Up" is; cancelling one also clears `auto_completed`/`completed_at` so the now-cancelled order doesn't carry stale "this was completed" bookkeeping; `bumpOrder(orderId)` stamps `priority_bumped_at` to move a live order to the front of its status lane, an explicit one-time vendor override with no cap on how often a live order can be re-bumped; `sweepReadyOrders()` is the ready-order auto-clear sweep — no id param, bulk-flips every `'ready'` order across the caller's own booths whose `ready_at` is older than the vendor's `board_settings.ready_auto_clear_min` (minutes; `null` disables the sweep) to `'completed'`, stamping `auto_completed: true` so it's distinguishable from a vendor's own "Mark Picked Up" tap; called on a 30s client poll from `realtime-order-board.tsx` (only while `ready_auto_clear_min` is set) rather than a DB cron job, returns `void` and only logs on failure since it's a background sweep with no toast, and the next poll simply retries — `OrderCard`'s "Mark Picked Up" shows a matching drain-bar countdown (`readyAutoClearMs` prop, `.autoclear-bar`) so this isn't invisible until the order just vanishes; `restoreAutoCompleted(orderId)` is the undo for a sweep that fired before the vendor actually collected the order — flips a `'completed'`+`auto_completed: true` order back to `'ready'` (clearing `completed_at`/`auto_completed`), rejecting any order that isn't in exactly that state (in particular, a vendor's own manual completion is never restorable through this path) — deliberately narrower than `revertOrderAdvance`'s short undo window since this is reached from a fresh page load (the completed-orders history list) with no client-held prior state. `confirmPaymentAndStart(orderId)` is the reconciled "Mark paid & start" review action (`OrderCard`, gated by `needsPaymentReview` in `@/lib/orders`) — there's no real scenario where a vendor confirms payment on a still-`pending` order without also starting it, so this confirms via paykit (same `createCheckout`/`confirmCheckout` call as `confirmOrderPayment`, so a `claimPayment` transaction doesn't stay stuck at `claimed` on paykit's side) then writes `status: 'preparing'` and `payment_status: 'confirmed'` in one guarded UPDATE instead of two separate taps; rejects an order that isn't `pending` or whose payment is already settled (`confirmed`/`not_required`). `revertPaymentAndStart(orderId, prevPaymentStatus)` is its undo, within `OrderCard`'s short undo window — a dedicated function rather than a widened `revertOrderAdvance`, since that one only restores `payment_status` when reverting from `'completed'`, not from `'preparing'`; reusing it here would silently leave `payment_status` at `'confirmed'` instead of undoing it.

Both show only when both kinds are ticked, which is the end-of-event case (a vendor who marked nothing all service clears the board in two taps). Each calls the existing `advanceOrder` action once per id (`Promise.all`, no new bulk RPC — each id still goes through its own optimistic-concurrency guard), toasts a success/failure count, and unticks the orders it just moved so a second tap cannot move them again; select mode ends when nothing is left ticked. Counts are taken against the orders on the board now, not the raw selection, since an order ticked while preparing may have been marked ready from another device. Only the QR area scrolls, so "Payment received" and "Collect later" stay pinned on a short screen. Nothing here detects that money arrived: PayNow and the pointer methods report nothing back, so the step always ends on a tap.
- `walkup-menu-actions.ts` — `getWalkupMenu(boothId)` server action: reads a booth's `menu_items` and `payment` config (RLS-scoped to the caller's own booths, same as the booth-edit page) plus its live `booth_remaining_stock` RPC result, for `WalkupOrderDialog` to render. Also derives `expectsPayment`/`paymentKind` from the booth's payment config via the local `markerKind` (a live, non-stripe kind counts; stripe is reserved but dark, same rule `place_walkup_order` applies) — reads just the `kind` discriminant rather than `parsePaymentConfig`'s full-shape parse, since `booths.payment` now stores only the minimal `{kind}` marker the paykit cutover writes (see `booths/actions.ts`), which the strict parse would reject outright. Unfiltered by `available`: same as the customer flow, an unavailable item is rejected server-side rather than hidden client-side.
- `walkup-order-dialog.dom.test.tsx` — RTL tests for `WalkupOrderDialog`: fetches the selected booth's menu once opened, adds a plain item and submits (asserts the exact `placeWalkupOrder` call including `paid=false` + dialog close), no payment control before the order is placed (and no payment wording at all at a booth that takes none), the payment step an unpaid order opens (title, amount, QR caption, dialog left open), "Payment received" confirming and closing, a failed confirm staying on the step, "Collect later" closing without confirming, the step still confirmable when the QR could not load, the order named by `displayNumber` in the title and both toasts, an event booth clearing for the next customer instead of closing (after a no-payment order, after "Payment received" and after "Collect later") with stock re-read and no loading flash, a no-booths empty state that skips the fetch entirely, and the disabled-submit-with-empty-cart state.
- `walkup-order-dialog.tsx` — `WalkupOrderDialog({ open, onOpenChange, booths, initialBoothId?, displayNumber? })` client component: a leaner, dashboard-scoped rebuild of `OrderForm`'s menu/cart UX (same `ItemCustomizer`, `cartKey`/`cartTotal`/`sumOptionDeltas`, stock-capping) for staff keying in a walk-up order. Deliberately drops `OrderForm`'s customer-only machinery (session/localStorage cart persistence, recent-orders, funnel events, redirect-on-success) and `PayPanel`'s customer-voiced polling UI. Payment is a second step, not a control on the order: the order is placed unpaid, and when `placeWalkupOrder` returns `payment` the dialog swaps its panes for `WalkupPayStep` (`./walkup-pay-step`) under a "Collect payment for order #N" title. "Payment received" calls `confirmOrderPayment` and closes; "Collect later", or just closing the dialog, leaves the ticket unpaid with its own "Mark as paid". A booth that takes no payment gets neither the step nor any payment wording; one that does shows a one-line "Payment comes next" note above the submit button. Split-pane `Dialog` (menu grid left, an order-summary column right holding the cart, customer-name field, and submit button) rather than a single scrolling sheet: a staff member building a multi-item order can see what's in the cart and hit submit without scrolling past the whole menu; panes stack on narrow screens. A booth `Select` appears only when more than one active booth is offered; the menu (re)fetches via `getWalkupMenu` whenever the open booth changes. Ignores menu responses from an earlier booth/opening and surfaces failed fetches. Submits through `placeWalkupOrder`, restores the submit control on rejection, toasts, and closes on success (or moves to the payment step). At an event booth (`booths[].walkup_default`) it does not close once an order is done (placed with nothing to pay, paid, or left for later): `nextCustomer` clears the cart, name and payment step and re-reads the menu and stock behind the cleared form with no loading state, so staff key in the next customer without reopening it. `menuRequest` numbers each menu request so a slow answer for an earlier booth, opening or customer is dropped. Every order number it shows (toasts, payment-step title) goes through `displayNumber`, defaulting to the permanent number when no board supplies one — the board itself updates via its existing realtime subscription, no manual state injection needed.

## Connectivity

`layout.tsx` gates every route under `/dashboard` (auth/vendor/admin/legal-acceptance redirects) and renders `dashboard-nav.tsx` around `{children}`; `page.tsx` is the `/dashboard` index route and renders `realtime-order-board.tsx`, which calls the order-mutation actions in `order-actions.ts` indirectly via `OrderCard` and subscribes through `@/hooks/use-realtime-orders`. `dashboard-nav.tsx` links out to `completed/`, `booths/`, `plan/`, `profile/`, `settings/`, `stats/`, `feedback/` — the dashboard's sub-routes for order history, booth management, billing, account, board preferences, analytics, and support respectively. `tour-actions.ts` is called by `DashboardTour` (in `@/components`) once the tour completes. `proof-actions.ts` is called by `PaymentProofViewer` (`@/components/payment-proof-viewer.tsx`), the OCR + duplicate-photo hint `OrderCard` opens on a claimed order's proof photo — not from anywhere else in this tree.
