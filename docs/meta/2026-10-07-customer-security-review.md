## Security and latency conclusions

Customer order reads/mutations consistently match unguessable access tokens; booth IDs and sequential order numbers alone do not authorize them. Service clients omit user cookies. Integration bearer checks fail closed and use timingSafeEqual. Notification helpers deliberately avoid use-server exports. Public display deliberately exposes order numbers/status only. No concrete service secret exposure was found.

Paykit/printkit fetches abort within 5 seconds, Merqo notification/loyalty within 3 seconds. Notifications are awaited despite fire-and-forget comments, so they can add network timeout latency to successful placement/claims. getWaitEstimate performs several sequential reads on every five-second customer tick; combine independent reads or share one polling snapshot before adding caching. Public token-minting render and printer-status endpoints lack their own throttle. No deployment timings were measured.

## Coverage and necessity

Most scope files serve concrete live routes. Do not delete compatibility redirect, token checks, separate capability secrets, component tests, or graceful-degradation branches as duplication. `getCheckoutStatus` has no production caller and is explicitly speculative; candidate for removal only if reconciliation does not adopt it. Bearer helper duplication intentionally represents different capabilities. Repeated display-number baseline reads and HTTP request wrappers could be consolidated only with demonstrated shared behavior, not blanket abstraction.

Regression priorities: anonymous collection preserves payment fields; preparing-to-ready mounts pickup QR; payment confirm removes stale pay instructions; undo reaches usable checkout; queue query excludes historical completions before row limiting; multi-page auth lookup; scanner rejected promise recovery; payment mirror reconciliation; simultaneous claim/unclaim/vendor confirmation; more than one page of financial data. Several current tests validate only mocked method chains and initial render, so they miss cross-component lifecycle and real RLS/query behavior.

The pickup toggle is documented as controlling QR visibility, while token possession is explicitly the collection authorization. This review does not reinterpret kiosk physical presence as a security guarantee. Live Supabase/paykit state, deployed limits, policy application, and browser/device behavior remain unverified.

## Remediation in this working tree

Implemented lifecycle-only anonymous collection (payment_status and paid_at remain untouched), server-page refresh on customer status transitions, usable /pay navigation after undo or a pending payment poll, refreshed server payment instructions after confirmation, UUID validation and flood limiting on public queue reads, database-side active/recent-completion filtering, and complete auth-user pagination with later-page failure propagation. Regression tests accompany these changes. The parent task captured the initial intended failing collection/poller/payment tests and owns the final focused/full verification; this report does not claim tests pass before that verification.

The second pass adds preclaim return/cancellation states and scanner exception recovery after the parent reproduced their failing tests. Already placed orders redirect to their numbered status page; cancelled orders cannot render the payment form. A failed scan releases the input and restores focus for a retry. The pickup flag remains a presentation toggle per the existing documented contract. Financial aggregation pagination is handled by the parent task; cross-service payment reconciliation remains a follow-up. Auth pagination fixes correctness but still scans shared auth accounts for each lookup; a server-owned indexed lookup is a future scalability improvement. The queue filter prevents historical completions consuming the response cap but does not paginate an exceptionally large live queue.

Fresh-eyes review of other agents' changes found one concrete realtime reconciliation gap: an UPDATE for an absent order arriving during resync was marked newer but not inserted locally, causing the snapshot row to be skipped. Reported to the vendor/UI owner for correction. No other blocking defect was found in the scoped CSV, stats pagination, walkup recovery, admin kit filter, or harness changes. Offset pagination is not a transactional snapshot during concurrent writes.

Next.js reference: [useRouter](https://nextjs.org/docs/app/api-reference/functions/use-router). The targeted installed guide path was absent; refresh is used to request updated Server Component content while retaining client state.
